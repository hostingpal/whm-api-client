# Agent Instructions

This project uses **bd** (beads) for issue tracking. Run `bd prime` for full workflow context.

> **Architecture in one line:** Issues live in a local Dolt database
> (`.beads/dolt/`); cross-machine sync uses `bd dolt push/pull` (a
> git-compatible protocol), stored under `refs/dolt/data` on your git
> remote — separate from `refs/heads/*` where your code lives.
> `.beads/issues.jsonl` is a passive export, not the wire protocol.
>
> See [sync-concepts](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md)
> for the one-screen overview and anti-patterns (don't treat JSONL as the
> source of truth; don't `bd import` during normal operation; don't
> reach for third-party Dolt hosting before trying the default).

## Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work atomically
bd close <id>         # Complete work
bd dolt push          # Push beads data to remote
```

## Non-Interactive Shell Commands

**ALWAYS use non-interactive flags** with file operations to avoid hanging on confirmation prompts.

Shell commands like `cp`, `mv`, and `rm` may be aliased to include `-i` (interactive) mode on some systems, causing the agent to hang indefinitely waiting for y/n input.

**Use these forms instead:**
```bash
# Force overwrite without prompting
cp -f source dest           # NOT: cp source dest
mv -f source dest           # NOT: mv source dest
rm -f file                  # NOT: rm file

# For recursive operations
rm -rf directory            # NOT: rm -r directory
cp -rf source dest          # NOT: cp -r source dest
```

**Other commands that may prompt:**
- `scp` - use `-o BatchMode=yes` for non-interactive
- `ssh` - use `-o BatchMode=yes` to fail instead of prompting
- `apt-get` - use `-y` flag
- `brew` - use `HOMEBREW_NO_AUTO_UPDATE=1` env var

## Agent Context Profile

This repository explicitly opts in to the **team-maintainer** profile
(`bd config get agent.profile` reports `team-maintainer`). There is no
conservative or minimal profile here: agents close beads, run quality gates,
commit, push, and open pull requests as part of every session that changes
files. The [Git Workflow](#git-workflow) section is authoritative.

## Session Completion

Every session that changes files ends with this protocol. Work is not complete
until it is committed, pushed, and has an open pull request against `master`.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** - See Build and Validation; never push failing gates
3. **Update issue status** - Close finished work, update in-progress items
4. **Commit, push, and open a pull request** from your branch:
   ```bash
   git status
   git add <changed files>
   git commit -m "<type>: <summary>"
   git fetch origin && git rebase origin/master
   git push -u origin HEAD
   gh pr create --base master --fill   # or push to the branch's existing PR
   bd dolt push
   ```
5. **Hand off** - Report the PR URL, validation, and issue status

**Critical rules:**
- Never commit to or push `master` directly; changes reach `master` only through pull requests.
- Never force-push shared branches or merge your own pull request unless the user asks.
- An explicit instruction from the user in the current session still overrides this block.
- If a commit, push, sync, or PR step fails, stop and report the exact command and error;
  never end a session with committed work that is not pushed.

## Architecture and Conventions

- Follow the [agreed PHP client interface](docs/superpowers/specs/2026-10-13-php-client-design.md):
  `whm()` and `uapi(?string $user = null)` expose typed operation groups; UAPI
  routes internally through direct cPanel access or WHM according to configured
  credentials. There is no separate public `bridge()` selector. WHM credentials
  require an explicit or configured default cPanel target; never assume `root`
  is that target. Preserve account isolation and per-client `responseMeta()`.
  Selectors and groups perform no I/O; every group method executes one request
  immediately and returns the documented payload as a plain array, scalar or `null`.
- Typed groups are generated (`src/Api/{Whm,Uapi}/**`, never edited by hand) from the
  pinned map plus `docs/api/overlay/`: UAPI groups per module, WHM groups per documented
  `x-tagGroups` entry; named arguments, plain arrays with generated PHPStan shapes, values
  normalized from observed wire variants recorded as overlay corrections with evidence.
  `docs/api/coverage.md` lists generated groups and exclusions. Handles route generated
  specs through `run()`/`dispatch()` and the shared request lifecycle.
- Generated surface details: results are arrays read with wire keys
  (`$client->uapi('npr')->domainInfo()->listDomains()['main_domain']`); omitted fields
  are absent keys and explicit nulls stay `null`. `whm()->accounts()->listAccounts()` and
  `accountSummary()` return the `acct` record list (`accountSummary()` does not require
  exactly one record); `hostingPlans()->listPackages()` returns the `pkg` list.
  `createAccount()`, `changePassword()` and `modifyAccount()` return `null` when the
  server sends no data (overlay `optional_payload`, engine `optional` spec key) and the
  documented array otherwise. Overlay `order` puts the key arguments first in
  `listAccounts(search, searchtype, searchmethod, want)`, `suspendAccount(user, reason, ...)`,
  `changePackage(user, package)`, `changePassword(user, password, ...)` and
  `verifyUserHasFeature(user, feature)`; prefer named arguments. Response validation
  enforces the effective PHP shape, required-field presence, null/omission rules
  and evidenced wire conversions. General minimum/range/enum constraints are not
  currently enforced; additions need explicit compatibility decisions per field
  or reviewed family (bead `whm-api-client-8x0.18`). Preserve existing integer
  bounds and flag rules. Combined alternatives do not establish exact JSON Schema
  validation; one server's observed values do not define a universal closed enum.
  Load averages keep `int|float|numeric-string` to preserve precision. Feature access
  returns true for unknown feature IDs by upstream design, and disabled-list values have
  inverted meaning. Pinned contracts, observed compatibility and runtime evidence stay
  separate; the read-only live suite passes through the generated groups on
  `test.oblak.host`.
- Generated groups receive one synchronous `run(spec, arguments)` callback from their
  handle, which clears the metadata first. The internal `OperationRunner` checks the
  whole spec before dispatch (`SpecChecker`: operation keys, every parameter spec and
  the full type grammar, cached per spec; `GeneratedSpecsTest` lints every generated
  spec offline), encodes the named arguments from the spec, dispatches through the
  handle (WHM and UAPI handles own route construction, with one account-bound UAPI
  helper for direct and bridged execution), validates the payload
  with `ShapeValidator` and the internal `PayloadReader`, which attaches the response
  snapshot to every failure, and unwraps the result. Reserved bridge fields take
  precedence over endpoint parameters. Generated multi-value parameters pass caller
  input through as `RepeatedList` (repeated keys, overlay encoding `repeat`) or
  `NumberedList` (WHM `name`, `name-1`, ..., encoding `numbered`); generic `call()` also
  accepts a plain `list<string>` as repeated keys. The shared encoder validates the
  contents after the metadata reset. Selectors only bind callbacks
  and cache groups; they perform no I/O or metadata reset.
- Requests declare their method and outcome policy. `RequestMethod::Get` places
  parameters in the query string; `RequestMethod::Post` keeps the routing fields
  (`api.version`, bridge `cpanel.*`) in the query string and form-encodes the
  operation parameters in the body, because the pinned WHM documentation says the
  server records query strings in its access log. Mutations and any operation with
  a secret-bearing parameter must use POST. `OutcomePolicy::Flag` (the documented
  `metadata.result`/`status` 1/0 rule) is the default typed policy; Features/has_feature
  uses unchecked UAPI status: integer 0 with no errors means absent/disabled and
  integer 1 means enabled. Nonempty errors means a failed call; inspect both.
  Typed unchecked UAPI still requires integer 0 or 1 before payload handling;
  `OutcomePolicy::Unchecked` records the envelope for operations whose status
  carries payload semantics; on the WHM bridge it waives only the UAPI status, and
  the outer WHM result is checked under both policies. Both require a usable envelope.
- `whm()->call()` and `uapi()->call()` are generic escape hatches: POST by default
  (GET only when passed explicitly), metadata cleared before name and parameter
  validation, reserved fields removed from caller parameters, `CallResult` with the payload
  converted to arrays and no schema. They support GET queries and form-encoded
  POST bodies only, with operation-specific parameter, route and envelope limits;
  JSON and multipart bodies remain unsupported on all routes. They are an escape
  hatch, not coverage; typed coverage comes from generation.
- Each attempt clears old response metadata. A usable envelope records an
  immutable snapshot before API or payload errors. `ResponseMetadata::$whm`
  retains raw WHM metadata; `$uapi` retains the UAPI result envelope without `data`.
  `ApiException::$metadata` exposes the same snapshot, with distinct
  `ApiErrorException`, `HttpException`, `InvalidResponseException`, and
  `TransportException` failures. A payload that fails its generated spec after the
  envelope and outcome were accepted raises the `PayloadMismatchException` subclass
  (`$outcomeConfirmed`, unvalidated `$payload`): writes are validated as strictly as
  reads, and callers must not retry a mutation that took effect (8x0.23). Both bridge
  outcomes are checked. Do not apply
  these operations' status semantics universally or claim generic bridge coverage.
  Typed metadata accessors and `errors()` read the documented envelope fields;
  `ApiException::errors()` exposes upstream error text outside `getMessage()`.
  `TransportException` records the PSR failure kind, cause class and token-redacted
  cause message without chaining the cause.
- Authenticated operations perform no retries. `Client` requires an explicit
  `HttpTransport`; its PSR-18 client must verify TLS, disable redirects and set
  timeouts, and `HttpTransport::discover()` is the explicit opt-in for unverified
  discovered defaults. The API layer rejects HTTP 3xx responses. Handles never
  expose `ClientConfig` or credentials, and credentials refuse serialization.
  Every library frame between a public method and the PSR-18 client that receives
  request parameters marks them `#[SensitiveParameter]`, so the library's trace
  frames carry no secrets even with `zend.exception_ignore_args=0`;
  `SensitiveTraceTest` searches them recursively for every failure type, including a
  client that throws inside `sendRequest()`. That client's own frame holds the
  request (token, GET query) and is outside the library's control.
  Direct UAPI supports the pinned `result` wrapper and the observed bare result
  object. A present `result` takes precedence even if malformed; the bare form
  requires top-level `status`. Authorized direct library verification on
  2026-10-13 for `DomainInfo/list_domains` as `npr` on `test.oblak.host:2083`
  passed with a cPanel token, the expected main domain, and HTTP 200/status 1.
  Keep this runtime evidence separate from pinned source contracts. Infrastructure
  tests and WHM bridge evidence do not establish other endpoint or route coverage.
- Production code lives in `src/`; tests live in `tests/` with a matching
  directory structure.
- `src/Http/HttpTransport.php` is the HTTP infrastructure entry point. It requires
  an explicit PSR-18 client; PSR-17 factories may be supplied or resolved through
  `php-http/discovery`, and `HttpTransport::discover()` opts in to a discovered client.
- Keep public HTTP contracts based on PSR interfaces. Do not couple the core
  runtime to Laravel, Guzzle, or another concrete HTTP implementation.
- Use PSR-12 plus the selected Slevomat rules in `phpcs.xml.dist`, strict types
  in PHP files, and the repository's `.editorconfig`. The focused rule set covers
  imports, arrays, trailing commas, spacing, and strict comparisons/calls; keep
  multiline arrow functions and PSR-12 spacing. Keep code compatible with
  PHPStan's maximum level.
- Test HTTP behavior with local doubles; routine tests must not require live
  WHM or cPanel services or credentials.
- User-authorized read-only slices should also be verified on `test.oblak.host`
  using the separate PHPUnit `live` group. Existing WHM root and cPanel `npr`
  tokens are supplied through `OBLAK_TEST_WHM_KEY` and `OBLAK_TEST_NPR_KEY`;
  never print or store them. No repeated permission is needed for implemented,
  reviewed read-only operations on this test server.
- **Standing test-account authorization (user confirmed 2026-10-15):** live tests
  may perform any operation on explicitly designated test accounts on
  `test.oblak.host`, including destructive operations and deletion. This covers
  existing test accounts as well as accounts created by a run. Do not ask again
  for each operation, target or rerun within that scope, and do not add a new
  snapshot-confirmation gate for those account-scoped tests. Bind each recipe to
  explicit test-account identifiers; this does not designate unrelated accounts
  as test accounts. Keep live opt-in, target guards and cleanup checks. Server-wide

## Documentation Requirements

- Document production classes, public APIs, configuration options, and
  non-obvious internal behavior as part of the implementation, not as a later
  cleanup task. Keep PHPDoc, usage examples, and README guidance current.
- Every hand-written API method (the generic `call()` methods and any future
  hand-written endpoint) must have a short PHPDoc summary and a separate
  detailed description covering its purpose, account scope, meaningful
  parameter behavior, returned payload, and relevant failure or metadata
  semantics. Use the reviewed source contract; do not invent missing details.
- Generated endpoint methods take their PHPDoc from the generator and are never
  edited by hand: the upstream summary and description, per-parameter text, the
  API-map identity, the operation `@see` link and the result shape, while the group
  docblock states the shared request, metadata and failure semantics. Record every
  caveat the upstream text lacks (irreversible operations, defaults that change
  behavior, role requirements, inverted meanings, observed wire behavior) as an
  overlay `note`, which renders in the method's PHPDoc, and regenerate.
- Include `@see` links to the exact official operation documentation on
  `https://api.docs.cpanel.net/` (the canonical cPanel developer documentation
  host). Add relevant guide links when authentication or bridge behavior needs
  context. Preserve the link between the PHP method and its pinned API-map
  identity; a link to the documentation homepage alone is not sufficient.
- Document array responses with precise PHPStan-compatible array shapes,
  including nested fields, optional keys, nullable values, and list element
  types. Use reusable `@phpstan-type` and `@phpstan-import-type` aliases where
  helpful. Apply the same precision to structured array inputs. Do not use bare
  `array` or `array<string, mixed>` as a substitute for a known endpoint schema.
- Generated methods return plain arrays; their PHPStan shapes are the contract
  and are never weakened to bare arrays. For genuinely opaque upstream metadata, explain
  the boundary instead of guessing a shape. Document applicable `@throws`
  contracts and preserve omitted, null, empty, and zero semantics.

## Git Workflow

All changes reach `master` through pull requests on
`github.com/hostingpal/whm-api-client`. This is enforced for every agent and
every session that changes files.

- Start each change on a branch from up-to-date `master`
  (`git fetch origin && git switch -c <type>/<topic> origin/master`) or in an agent
  worktree branch. Never commit directly to `master`.
- Commit in logical units with conventional messages (`feat:`, `fix:`,
  `refactor:`, `docs:`, `test:`, `chore:`).
- Before pushing, run `composer validate` and `composer check`, plus
  `composer api-map:check` when `tools/api-map`, anything under `docs/api/`, or generated
  code change. Do not push failing gates; if a gate cannot pass, open
  a draft pull request that says why.
- Push the branch (`git push -u origin HEAD`) and open a pull request against
  `master` with `gh pr create`. Describe the changes, validation (including live
  results when run), and the beads closed. Use a draft for incomplete work, and
  push follow-up commits to the same pull request.
- Run `bd dolt push` after creating, updating, or closing beads so issue state
  reaches the remote.
- Never force-push shared branches, rewrite `master`, merge your own pull request,
  or bypass branch protection unless the user explicitly asks.
- The repository is public. Never commit credentials, tokens, live payloads,
  capability profiles, or `.cache/` artifacts.
- If any commit, push, sync, or pull request step fails, stop and report the
  exact command and error.
