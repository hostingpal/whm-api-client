## Non-Interactive Shell Commands

**ALWAYS use non-interactive flags** with file operations to avoid hanging on confirmation prompts.

Shell commands like `cp`, `mv`, and `rm` may be aliased to include `-i` (interactive) mode on some systems, causing the agent to hang indefinitely waiting for y/n input.

**Use these forms instead:**
```bash
# Force overwrite without prompting
cp -f source dest           # NOT: cp source dest
mv -f source dest           # NOT: mv source dest
rm -f file                  # NOT: rm file

# For recursive operations
rm -rf directory            # NOT: rm -r directory
cp -rf source dest          # NOT: cp -r source dest
```

**Other commands that may prompt:**
- `scp` - use `-o BatchMode=yes` for non-interactive
- `ssh` - use `-o BatchMode=yes` to fail instead of prompting
- `apt-get` - use `-y` flag
- `brew` - use `HOMEBREW_NO_AUTO_UPDATE=1` env var

## Agent Context Profile

This repository explicitly opts in to the **team-maintainer** profile
(`bd config get agent.profile` reports `team-maintainer`). There is no
conservative or minimal profile here: agents close beads, run quality gates,
commit, push, and open pull requests as part of every session that changes
files. The [Git Workflow](#git-workflow) section is authoritative.

## Session Completion

Every session that changes files ends with this protocol. Work is not complete
until it is committed, pushed, and has an open pull request against `master`.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** - See Build and Validation; never push failing gates
3. **Update issue status** - Close finished work, update in-progress items
4. **Commit, push, and open a pull request** from your branch:
   ```bash
   git status
   git add <changed files>
   git commit -m "<type>: <summary>"
   git fetch origin && git rebase origin/master
   git push -u origin HEAD
   gh pr create --base master --fill   # or push to the branch's existing PR
   bd dolt push
   ```
5. **Hand off** - Report the PR URL, validation, and issue status

**Critical rules:**
- Never commit to or push `master` directly; changes reach `master` only through pull requests.
- Never force-push shared branches or merge your own pull request unless the user asks.
- An explicit instruction from the user in the current session still overrides this block.
- If a commit, push, sync, or PR step fails, stop and report the exact command and error;
  never end a session with committed work that is not pushed.

## Project Scope

`hostingpal/whm-api-client` is a standalone PHP Composer library in the
`HostingPal\WhmApiClient` namespace. Its planned scope is the complete WHM API
and cPanel UAPI surface, delivered as generated typed groups. Operation and group
totals are a fact of construction: read them from `docs/api/coverage.md`, not
from prose.

Official API inputs and contract discrepancies are pinned under `docs/api/`. Do not invent
endpoints, authentication rules, request payloads, or response schemas to fill
gaps in those sources.

The core package must remain framework-independent. A future Laravel
integration belongs in a separate Composer package and will use Guzzle. The
Go documentation tool under `tools/api-map/` produces a canonical API map;
further commands are tracked under `gwi`. Go is a
development-tool choice, not a runtime dependency of the PHP package. Preserve pinned documentation snapshots and
refresh them explicitly; routine checks must remain offline. The tool design
is tracked under `whm-api-client-gwi`; Laravel integration is separate work.

## Architecture and Conventions

Bullets below that summarize runtime behavior are detailed in
[docs/agents/architecture.md](docs/agents/architecture.md). Read the relevant part
before changing `src/` runtime code, the generator or request encoding.

- Follow the [agreed PHP client interface](docs/superpowers/specs/2026-10-13-php-client-design.md):
  `whm()` and `uapi(?string $user = null)` expose typed operation groups; UAPI
  routes internally through direct cPanel access or WHM according to configured
  credentials. There is no separate public `bridge()` selector. WHM credentials
  require an explicit or configured default cPanel target; never assume `root`
  is that target. Preserve account isolation and per-client `responseMeta()`.
  Selectors and groups perform no I/O; every group method executes one request
  immediately and returns the documented payload as a plain array, scalar or `null`.
- Typed groups are generated (`src/Api/{Whm,Uapi}/**`, never edited by hand) from the
  pinned map plus `docs/api/overlay/`: UAPI groups per module, WHM groups per documented
  `x-tagGroups` entry; named arguments, plain arrays with generated PHPStan shapes, values
  normalized from observed wire variants recorded as overlay corrections with evidence.
  `docs/api/coverage.md` lists generated groups and exclusions. Handles route generated
  specs through `run()`/`dispatch()` and the shared request lifecycle.
- Generated results are plain arrays read with wire keys; omitted fields are absent
  keys and explicit nulls stay `null`. Response validation enforces the effective PHP
  shape, required-field presence, null/omission rules and evidenced wire conversions.
  General minimum/range/enum constraints are not enforced; adding one needs an explicit
  compatibility decision per field or reviewed family (bead `whm-api-client-8x0.18`).
  One server's observed values never define a closed enum. Keep pinned contracts,
  observed compatibility and runtime evidence separate.
- Generated groups call one synchronous `run(spec, arguments)` on their handle, which
  clears the metadata first. `OperationRunner` checks the whole spec (`SpecChecker`;
  `GeneratedSpecsTest` lints every generated spec offline), encodes the arguments
  (`ArgumentEncoder` into `OrderedFields`), dispatches through the handle, validates
  the payload (`ShapeValidator`, `PayloadReader`) and unwraps the result. Wire-name
  collisions and routing reservations (the whole `api.` prefix; on the bridge also
  `cpanel.user`, `cpanel.module` and `cpanel.function`) are rejected before I/O. All
  argument validation follows the metadata reset; form names and values are encoded
  once. Selectors only bind callbacks and cache groups; they perform no I/O or
  metadata reset.
- Requests declare their method and outcome policy. `RequestMethod::Get` places
  parameters in the query string; `RequestMethod::Post` keeps the routing fields
  (`api.version`, bridge `cpanel.*`) in the query string and form-encodes the
  operation parameters in the body, because the pinned WHM documentation says the
  server records query strings in its access log. Mutations and any operation with
  a secret-bearing parameter must use POST. `OutcomePolicy::Flag` (the documented
  `metadata.result`/`status` 1/0 rule) is the default typed policy; Features/has_feature
  uses unchecked UAPI status: integer 0 with no errors means absent/disabled and
  integer 1 means enabled. Nonempty errors means a failed call; inspect both.
  Typed unchecked UAPI still requires integer 0 or 1 before payload handling;
  `OutcomePolicy::Unchecked` records the envelope for operations whose status
  carries payload semantics; on the WHM bridge it waives only the UAPI status, and
  the outer WHM result is checked under both policies. Both require a usable envelope.
- `call()`, `callJson()` and `callMultipart()` on `whm()` and `uapi()` are untyped
  escape hatches that return `CallResult`. `call()` supports GET queries and form POST
  only; `callJson()` and `callMultipart()` work through WHM and direct UAPI, and bridged
  UAPI rejects them locally. They establish no typed or live coverage: typed coverage
  comes only from generation. One invocation is one attempt.
- Each attempt clears old response metadata, and a usable envelope records an immutable
  snapshot before API or payload errors (`responseMeta()`, `ApiException::$metadata`).
  Failures stay distinct: `ApiErrorException`, `HttpException`,
  `InvalidResponseException`, `TransportException`, and `PayloadMismatchException`
  (`$outcomeConfirmed`, unvalidated `$payload`) when a payload fails its generated spec
  after the outcome was accepted. Writes are validated as strictly as reads; callers
  must not retry a mutation that took effect (8x0.23).
- Authenticated operations perform no retries; the single development-only exception
  is the cleanup-ownership re-read in
  `tools/live-verify/src/DisposableAccountLifecycle.php`. `Client` requires an explicit
  `HttpTransport` whose PSR-18 client verifies TLS, disables redirects and sets
  timeouts; `HttpTransport::discover()` is the explicit opt-in for discovered defaults.
  The API layer rejects HTTP 3xx responses. Handles never expose `ClientConfig` or
  credentials, and credentials refuse serialization. Every library frame that receives
  request parameters marks them `#[SensitiveParameter]`; `SensitiveTraceTest` enforces
  this for every failure type.
- Production code lives in `src/`; tests live in `tests/` with a matching
  directory structure.
- `src/Http/HttpTransport.php` is the HTTP infrastructure entry point. It requires
  an explicit PSR-18 client; PSR-17 factories may be supplied or resolved through
  `php-http/discovery`, and `HttpTransport::discover()` opts in to a discovered client.
- Keep public HTTP contracts based on PSR interfaces. Do not couple the core
  runtime to Laravel, Guzzle, or another concrete HTTP implementation.
- Use PSR-12 plus the selected Slevomat rules in `phpcs.xml.dist`, strict types
  in PHP files, and the repository's `.editorconfig`. The focused rule set covers
  imports, arrays, trailing commas, spacing, and strict comparisons/calls; keep
  multiline arrow functions and PSR-12 spacing. Keep code compatible with
  PHPStan's maximum level.
- Test HTTP behavior with local doubles; routine tests must not require live
  WHM or cPanel services or credentials.
- User-authorized read-only slices should also be verified on `test.oblak.host`
  using the separate PHPUnit `live` group. Existing WHM root and cPanel `npr`
  tokens are supplied through `OBLAK_TEST_WHM_KEY` and `OBLAK_TEST_NPR_KEY`;
  never print or store them. No repeated permission is needed for implemented,
  reviewed read-only operations on this test server.
- **Standing test-account authorization (user confirmed 2026-10-15):** live tests

## Documentation Requirements

- Document production classes, public APIs, configuration options, and
  non-obvious internal behavior as part of the implementation, not as a later
  cleanup task. Keep PHPDoc, usage examples, and README guidance current.
- Every hand-written API method (the generic `call()` methods and any future
  hand-written endpoint) must have a short PHPDoc summary and a separate
  detailed description covering its purpose, account scope, meaningful
  parameter behavior, returned payload, and relevant failure or metadata
  semantics. Use the reviewed source contract; do not invent missing details.
- Generated endpoint methods take their PHPDoc from the generator and are never
  edited by hand: the upstream summary and description, per-parameter text, the
  API-map identity, the operation `@see` link and the result shape, while the group
  docblock states the shared request, metadata and failure semantics. Record every
  caveat the upstream text lacks (irreversible operations, defaults that change
  behavior, role requirements, inverted meanings, observed wire behavior) as an
  overlay `note`, which renders in the method's PHPDoc, and regenerate.
- Include `@see` links to the exact official operation documentation on
  `https://api.docs.cpanel.net/` (the canonical cPanel developer documentation
  host). Add relevant guide links when authentication or bridge behavior needs
  context. Preserve the link between the PHP method and its pinned API-map
  identity; a link to the documentation homepage alone is not sufficient.
- Document array responses with precise PHPStan-compatible array shapes,
  including nested fields, optional keys, nullable values, and list element
  types. Use reusable `@phpstan-type` and `@phpstan-import-type` aliases where
  helpful. Apply the same precision to structured array inputs. Do not use bare
  `array` or `array<string, mixed>` as a substitute for a known endpoint schema.
- Generated methods return plain arrays; their PHPStan shapes are the contract
  and are never weakened to bare arrays. For genuinely opaque upstream metadata, explain
  the boundary instead of guessing a shape. Document applicable `@throws`
  contracts and preserve omitted, null, empty, and zero semantics.

## Build and Validation

Run commands from the repository root:

```bash
composer install --no-interaction
composer validate
composer check
```

`composer check` runs the PSR-12/Slevomat formatting check, static analysis, and
tests. The individual commands are:

```bash
composer phpcs
composer phpcbf
composer phpstan
composer test
```

`composer phpcbf` applies formatting fixes. Tool configuration lives in
`phpcs.xml.dist` (PSR-12 and selected Slevomat rules), `phpstan.neon.dist` (maximum level), and
`phpunit.xml.dist`.

PHPCS resolves Slevomat through the ruleset's explicit `installed_paths` setting.
The Composer standards-installer plugin remains disabled; do not require a
global PHPCS configuration or introduce WordPress runtime dependencies.

Explicit live verification (PHP cURL extension and both test tokens exported):

```bash
WHM_API_LIVE=1 composer test:live
```

The live suite/group exercises only the reviewed read-only GET and POST requests
for implemented operations on `test.oblak.host`, with verified TLS, redirects
disabled, and no retries. Missing opt-in or credentials fail before network I/O.
Default PHPUnit, Composer checks and CI remain offline even when credentials are
present. Keep raw live payloads, credentials and profiles outside committed fixtures.

The opted-in account lifecycle (`tests/Live/AccountLifecycleLiveTest.php`, group
`live-mutating`) is excluded from `composer test:live`. The current harness creates
and removes exactly the throwaway account named by `WHM_API_LIVE_ACCOUNT` and runs
only with `WHM_API_LIVE=1 WHM_API_LIVE_MUTATIONS=1 WHM_API_LIVE_ACCOUNT=<user>
WHM_API_LIVE_DOMAIN=<domain>`; its transport guard refuses other mutations. Its
creation flow requires the account to be absent first. That is a harness invariant,
not a restriction on the standing authorization for other tests to use existing
explicitly designated test accounts. The lifecycle ran green on 2026-10-15; runs
within the standing test-account scope need no repeated approval.

Go documentation tooling (Go 1.24+) uses a separate module and cache:

```bash
export GOCACHE="$PWD/.cache/go-build"
export GOMODCACHE="$PWD/.cache/go-mod"
go -C tools/api-map test ./...
go -C tools/api-map run ./cmd/api-map sources verify --manifest ../../docs/api/sources/2026-10-13/manifest.json
go -C tools/api-map run ./cmd/api-map map build --manifest ../../docs/api/sources/2026-10-13/manifest.json --annotations ../../docs/api/annotations.json --output ../../.cache/api-map/map.json
sha256sum -c docs/api/map.sha256
```

The map build validates before atomically replacing its output. Pinned sources,
reviewed hash-bound annotations, and ordinary checks remain offline. Only an
explicit `sources refresh --manifest PATH --output-dir NEW_DIR` command may
fetch documentation; it validates a new immutable snapshot. Review annotations
again when their source hashes change. Maps retain upstream response envelopes
and BasicAuth alongside token-guide evidence. Generated large maps live under
`.cache/api-map/`; `docs/api/map.sha256` records the reviewed deterministic map.
`composer check` continues to validate the PHP package offline.

Live capability capture is a separate, explicitly opted-in command, never a
routine check:

```bash
go -C tools/api-map run ./cmd/api-map capabilities capture --opt-in --host https://test.oblak.host:2087 --user root --token-env OBLAK_TEST_WHM_KEY --output ../../.cache/api-map/capability-profile.json
```

Capture only requests WHM `version` and `applist`. Keep real credentials and
profiles outside committed fixtures. UAPI runtime inventory remains unavailable;
WHM bridge evidence never establishes direct UAPI authentication.



Offline toolchain integration (Go 1.24+, Composer dependencies installed):

```bash
composer api-map:check
go -C tools/api-map vet ./...
go -C tools/api-map generate ./internal/schema
```

`api-map:check` runs `check --root ../..`, reading `docs/api/toolchain.json`.
It builds in temporary storage, checks exact schema copies/map reproducibility,
the overlay against the map, that committed generated code is current (including
stale generated files), and synthetic capability/drift examples. It is read-only
and offline. Invalid input, overlay problems or stale generated code exit 1. Live
verification never affects the offline checks. Keep `composer check` PHP-only.
See `tools/api-map/README.md` for explicit artifact regeneration and the saved
`capabilities compare` / `drift report` commands. The CI workflow uses locked
dependencies and receives no WHM/cPanel secrets.

Generated client from the pinned map and `docs/api/overlay/` (offline; see the
overlay rules in `tools/api-map/README.md`):

```bash
composer api-map:generate        # build the map, then write generated PHP and docs/api/coverage.md
composer api-map:generate:check  # fail on overlay problems or stale generated files
```

Generated files carry the marker line `Generated by tools/api-map from the pinned
API map and docs/api/overlay; do not edit.` and are never edited by hand: change
the overlay or the generator and regenerate. Every overlay correction and
exclusion needs evidence (`doc` or `live`, version, date, note). Coverage is a fact
of construction: `docs/api/coverage.md` lists generated groups and exclusions.


## Git Workflow

All changes reach `master` through pull requests on
`github.com/hostingpal/whm-api-client`. This is enforced for every agent and
every session that changes files.

- Start each change on a branch from up-to-date `master`
  (`git fetch origin && git switch -c <type>/<topic> origin/master`) or in an agent
  worktree branch. Never commit directly to `master`.
- Commit in logical units with conventional messages (`feat:`, `fix:`,
  `refactor:`, `docs:`, `test:`, `chore:`).
- Before pushing, run `composer validate` and `composer check`, plus
  `composer api-map:check` when `tools/api-map`, anything under `docs/api/`, or generated
  code change. Do not push failing gates; if a gate cannot pass, open
  a draft pull request that says why.
- Push the branch (`git push -u origin HEAD`) and open a pull request against
  `master` with `gh pr create`. Describe the changes, validation (including live
  results when run), and the beads closed. Use a draft for incomplete work, and
  push follow-up commits to the same pull request.
- Run `bd dolt push` after creating, updating, or closing beads so issue state
  reaches the remote.
- Never force-push shared branches, rewrite `master`, merge your own pull request,
  or bypass branch protection unless the user explicitly asks.
- The repository is public. Never commit credentials, tokens, live payloads,
  capability profiles, or `.cache/` artifacts.
- If any commit, push, sync, or pull request step fails, stop and report the
  exact command and error.

## Maintaining Agent Guidance

`AGENTS.md` is the single source of agent guidance. `CLAUDE.md` only imports it
(`@AGENTS.md`), so Claude Code and other agents read identical instructions.
Edit `AGENTS.md`, keep `CLAUDE.md` as the import, and do not add a separate
Beads block to `CLAUDE.md` (do not run `bd setup claude` to re-add one).
Preserve the generated Beads blocks and keep project-specific additions outside
them. If `bd setup` regenerates a Beads block with profile-neutral wording,
re-apply the team-maintainer wording; the Git Workflow section is authoritative.

Keep `AGENTS.md` under 32,000 bytes (`wc -c AGENTS.md`). The whole file is loaded
into every session: Codex stops reading project instructions at 32 KiB by default
(`project_doc_max_bytes`) and Claude Code warns above 40,000 characters. It holds
only rules that apply to every session; module contract notes, recipe state and
runtime detail belong in `docs/agents/` (see [Module Contract Notes](#module-contract-notes)).
