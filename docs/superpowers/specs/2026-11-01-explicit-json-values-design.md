# Explicit free-form JSON values — design

Implements the owner-approved rule: keep ordinary PHP arrays for known schemas; require an explicit object/list choice where a value can be arbitrary JSON. Preserve and validate values. Keep callJson as the raw complete-body escape hatch. The owner resumed autonomous slice implementation; the interface choices below are implementation rulings, not new owner quotations.

## Approach and scope
Use two small final readonly value descriptors in HostingPal\WhmApiClient: JsonObject and JsonList. This extends the existing schema-directed serializer, not PHP object auto-serialization. Ordinary closed object/list schemas retain their existing array input and validation. stdClass, arbitrary objects, resources and JsonSerializable remain rejected. Unknown serialized strings stay strings. This PR supplies the foundation, generator lowering and focused synthetic integration coverage; no newly typed endpoint or live coverage is counted. save_connected_application adoption, optional WHM bodies, missing formal container types and ambiguous schema unions stay separate.

Factories:
- JsonObject::fromArray(array $members): self for normal string-name maps.
- JsonObject::fromEntries(array $entries): self for a sequential list of exact records {name: string, value: mixed}; permits numeric JSON names without PHP key coercion. Reject duplicate names, extra/missing entry fields and invalid names during encoding. Empty entries means {}.
- JsonList::fromArray(array $items): self for a sequential list. Empty means [].
Factories only wrap input, with SensitiveParameter on their arguments. Content validation happens during the existing operation attempt after metadata reset, before I/O, like the existing list markers. Native non-array TypeErrors before factory entry retain ordinary PHP behavior. Descriptor arrays follow PHP reference semantics; do not promise a deep immutable snapshot. Runtime traversal must reject reference cycles within the total depth bound. Avoid magic serialization/callbacks, parsing or side effects. Document that descriptor contents may contain secrets, as ordinary input arrays do.

## Schema and value rules
Add an internal strict request descriptor type json for unrestricted JSON values. It accepts null, native bool/int, finite float, UTF-8 string, JsonObject or JsonList. Bare PHP arrays in this unrestricted position are rejected because their object/list kind is not explicit. Wrapper content recurses using the same json value grammar. Reject NAN/INF, invalid UTF-8 names/values, resources and all other objects without invoking user callbacks. Retain FloatEncoder value/1.0 preservation, insertion/list order, empty strings, null, false and zero. No scalar coercion, normalization, trimming or enum inference.

Known object schemas with unrestricted additional values (values.type=json) accept their usual PHP string-key array or JsonObject. Both forms validate known fields by their own schema, requiredness/nullability and all undeclared members by the unrestricted grammar. Thus an explicit open object can carry numeric-string member names through fromEntries without weakening known fields. Closed objects, typed-value maps and known list schemas keep their existing array-only boundary. JsonList is accepted only where an unrestricted value permits a list. Keep precise generated array shapes plus the explicit JsonObject alternative for open objects; do not replace known fields with mixed.

All containers, whether schema-known arrays or explicit descriptors, share the existing maximum511 nested container budget and final json_validate(...,512) check. Scalars add no depth. Cyclic arrays/descriptors must fail with a safe local InvalidArgumentException before network I/O. Malformed descriptors fail with LogicException. json includes null intrinsically; keep acceptsNull and optional-body/field ambiguity checks correct. json cannot join the existing disjoint-scalar union grammar because its domain overlaps every type. Existing scalar unions remain unchanged.

Generator lowering recognizes explicitly unrestricted additionalProperties only: literal true or exactly empty schema object {} under an explicitly typed object in an already evidence-bound structured input source. Missing type on roots, properties, items, composed schemas or nonempty untyped additional schemas remains a source gate. Do not infer arbitrary JSON from a failed schema resolution. Existing required source-hash/requestBody (or parameter) evidence remains mandatory. Add exact source-context tests and preserve unrelated effective schemas. A new json node is not a valid whole JSON body root; existing nonnullable-object/required-WHM/direct-route rules remain.

## Routing and privacy
Raw callJson is unchanged. Typed JSON encoding still passes through existing JsonBody guards: case-sensitive entire root api. namespace and direct-UAPI cpanel routing keys remain forbidden even when supplied via an explicit root/open object. Nested names remain data. Bridged JSON still rejects after reset before I/O. No query/body fallback, retry, auth action or implicit conversion.
Every value-bearing constructor/factory/encoder/helper/closure trace frame must be sensitive; static error messages must not echo values or member names. Do not expose JsonSerializable hooks. Tests must include sentinels in failed nested values/names and exception traces.

## Validation
Tests first for {} versus [], nested mixed values, string versus parsed JSON, numbers/1.0, ordering, numeric-string and leading-NUL names, duplicate names, malformed entry/list shapes, ordinary arrays rejected in unrestricted positions, known schemas unchanged, known-field enforcement in open JsonObject, null omission rules, invalid schema unions, UTF-8 and nonfinite values, depth510/511/512 and cycles including external reference cycles. Use independent expected wire strings and a generated synthetic whole-body/JSON-valued-field call. Verify metadata reset, no I/O on invalid input, generic/raw preservation, root reservations and bridge refusal. Generator tests cover true/{} additional source nodes and nearby missing-type/unknown-schema cases; no committed existing generated endpoint changes expected. All existing source/evidence files remain byte-identical.
